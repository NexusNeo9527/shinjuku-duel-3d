# 五个新 GLB 的移动端开销与优化

本地完成于 2026-10-06。保持建筑、手掌、指节、掌纹、屋瓦、树木、招牌、裂纹和碎石设计；没有减面、改变顶点位置、三角形绕序、材质参数、节点变换或碰撞标记。

## 开销来源与实施

五个文件都没有纹理，所以没有贴图解码或纹理显存瓶颈。真人领域有 73,680 个三角形，高专初战有 60,432 个三角形；高专屋瓦和植被使用大量带硬边法线的顶点。静态装饰已经按材质合并。涩谷最终战的 110 个网格中大量为独立碎石，这使 CPU 提交开销相对突出。游戏移动端原本已经关闭阴影并限制 DPR 到 1.3；深度预通道仍会重复绘制可见场景。

1. 五个 GLB 使用 `KHR_mesh_quantization` 将法线从 Float32 改为归一化 Int16，保留 Float32 位置。每个法线分量舍入误差不超过约 0.00001526。16 位法线的 GLB 布局按规范采用 8 字节步长；统计包含这部分对齐，未将理论上的 6 字节误算为实际上传开销。项目 Three.js r169 的 GLTFLoader 原生支持该扩展，不需要额外解码器。
2. 仅合并位置和原法线都完全相同的顶点，保留硬边。高专初战顶点从 119,248 降到 114,464。没有删除三角形，包括原模型中的退化三角形。
3. 仅在移动端对四个战场启用碎石区域批次，按原材质和 32 米区域分组。原网格保留为独立命中代理，渲染层关闭；新批次共享原材质。建筑碰撞体不参与合并。命中后更新索引的可见区间，重选关卡时恢复，不在每帧重建几何。每次命中最多破坏 8 块的行为保持原样。原始代理几何仍占 CPU 内存，但不会上传到 GPU；因此下表没有宣称等量的总进程内存下降。

## 模型前后对比

MiB = 1,048,576 字节。几何缓冲统计位置、法线（含对齐）和索引，在移动端计入可绘制区域批次，排除不绘制的命中代理；不含帧缓冲、环境贴图、后处理、驱动分配和 CPU 副本。全景调用是单次模型绘制通道全部网格可见时的实际 `renderer.info.render.calls`，不是整场战斗每帧调用总数。

| 场景 | GLB MiB 前 → 后 | 文件减少 | 几何缓冲 MiB 前 → 后 | 全景调用 前 → 后 | 三角形 前 = 后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 真人领域 | 1.665 → 1.458 | 12.4% | 1.659 → 1.452 | 6 → 6 | 73,680 |
| 怀玉初战 | 3.084 → 2.540 | 17.6% | 3.075 → 2.529 | 13 → 13 | 60,432 |
| 怀玉再战 | 0.535 → 0.464 | 13.4% | 0.519 → 0.429 | 42 → 27 | 10,104 |
| 涩谷共斗 | 0.786 → 0.689 | 12.3% | 0.747 → 0.634 | 65 → 35 | 14,604 |
| 涩谷最终战 | 0.770 → 0.690 | 10.4% | 0.705 → 0.596 | 110 → 37 | 13,828 |

总文件从 7,172,484 降到 6,125,368 字节，减少 **14.6%**；可绘制几何缓冲从 7,030,560 降到 5,913,624 字节，减少 **15.9%**。这五个资源是在不同场景使用，合计值表示资源库存，不能视为某一帧的同时绘制开销。

## 验证与限制

- `node tools/optimize-latest-arenas.js --check`：三角形展开位置与绕序、规范化法线、节点、场景及材质摘要与优化前一致；校验当前开销与移动批次数。
- `npm run verify:story`：实际 GLTFLoader 解析、碰撞框一致性、独立碎石世界坐标、命中上限、可见三角形减少和关卡重置恢复通过。四个战场仍有 6 / 11 / 13 / 13 个碰撞体。
- `npm run build` 与 `git diff --check` 通过。
- Edge / ANGLE SwiftShader，移动视口 844×390、DPR 1.3、关闭阴影及后处理的隔离绘制验证：无脚本或 WebGL 错误。检查全景、地面、对角三个视角；领域检查内部视角。合并前后采用同一份压缩后模型，最多 4 个像素的 RGB 通道差值超过 3/255，最大平均通道差值小于 0.0005/255。此项比较验证批次外观；法线压缩由误差界和模型摘要验证。
- 实际 Renderer3D 移动模式巡览五个场景通过，截图为 `art/mobile-optimized-shibuyaFinal.png` 和 `art/mobile-optimized-mahito.png`。

区域合并使剔除粒度变粗：涩谷共斗地面视角提交三角形 14,280 → 14,424，调用 38 → 26；最终战 13,216 → 13,516，调用 59 → 26。全景三角形完全相同。这是用少量额外顶点处理换取更少绘制调用的明确代价。领域和高专初战已有很少的调用，本次集中减少它们的缓冲与传输，不再粗化轮廓。

软件渲染验证不能代表手机 GPU 帧率或温度；尚未获得真机 FPS、GPU 时间或峰值进程内存。原有双面材质与后处理保留，因此双面像素填充和战斗特效仍可能构成设备瓶颈。改动没有提交或推送。

## 复现

原始设计继续保存在 `art/latest-arenas.blend` 和 `tools/build_latest_arenas.py`。重新导出同一设计后运行 `node tools/optimize-latest-arenas.js`，随后运行 `--check` 和剧情回归。优化器对已经优化的资产不重复改写。设计发生变化时应重新建立基线报告，再进行前后比较。

原始数值与摘要：`docs/latest-arena-costs.json`。浏览器绘制实测：`docs/latest-arena-render-costs.json`。启动 Vite 后访问 `/tools/arena-cost-preview.html` 可复现绘制与像素比较；`/tools/arena-preview.html` 可检查游戏渲染器中的场景。
